# Linting

How ESLint is wired across the monorepo, and what a new workspace package must
ship so `pnpm lint` keeps passing.

## Architecture

ESLint 9 **flat config**. There is no root config file — each workspace owns its
own `eslint.config.*`, and shared rules come from `packages/eslint-config`.

A legacy root `.eslintrc.js` used to exist. It was deleted: ESLint 9 ignores the
eslintrc format entirely, so its `ignorePatterns` never applied. Don't
reintroduce one — the shared ignores live in `packages/eslint-config/base.js`.

`packages/eslint-config` exposes three entry points:

| Import subpath | File | Use for |
| --- | --- | --- |
| `@workspace/eslint-config/base` | `base.js` | Non-React TypeScript packages |
| `@workspace/eslint-config/react-internal` | `react-internal.js` | React libraries and non-Next React apps |
| `@workspace/eslint-config/next-js` | `next.js` | Next.js apps |

Note the mismatch: the subpath is `next-js` but the file is `next.js`. Import the
subpath, not the filename.

`base.js` supplies the shared ignores (`dist/**`, `.next/**`, `**/.turbo/**`,
`**/coverage/**`) and is spread into the other two, so every package inherits
them.

## Adding lint to a new package

Three things are required. Missing any one of them breaks `pnpm lint`
workspace-wide, because `turbo lint` aborts on the first failing task.

**1. Add the shared config as a devDependency.** A config file alone will not
resolve — this is the step that is easy to forget:

```json
"devDependencies": {
  "@workspace/eslint-config": "workspace:*"
}
```

**2. Add a `lint` script:**

```json
"scripts": { "lint": "eslint" }
```

**3. Add the config file**, picking the entry point from the table above:

```js
import { config } from "@workspace/eslint-config/base"

/** @type {import("eslint").Linter.Config} */
export default config
```

Then run `pnpm install` to relink the new workspace dependency.

### The `.mjs` gotcha

If the package's `package.json` has **no `"type": "module"`**, a plain
`eslint.config.js` is parsed as CommonJS and the `import` throws. Name the file
**`eslint.config.mjs`** instead.

`apps/studio` is the live example — it is the one package in this repo without
`"type": "module"`, so it uses `eslint.config.mjs`. Every other workspace is ESM
and uses `eslint.config.js`.

### Extending with package-specific ignores

Spread the shared config and append:

```js
import { config } from "@workspace/eslint-config/base"

/** @type {import("eslint").Linter.Config} */
export default [
  ...config,
  { ignores: ["src/sanity.types.ts"] },
]
```

What is ignored today, and why:

- `packages/sanity` → `src/sanity.types.ts` — generated by
  `pnpm --filter studio type`, never hand-edited. See
  [`sanity-workflow.md`](./sanity-workflow.md).
- `apps/studio` → `.sanity/` (generated runtime), `vendor/` (vendored
  third-party bundle), `dist/` (build output), `schema.json` (generated by
  `sanity schema extract`).

## Lint is currently non-blocking

`base.js` loads `eslint-plugin-only-warn`, which downgrades **every** rule to a
warning. `eslint` therefore exits 0 no matter what it finds.

**A green `pnpm lint` does not mean zero findings.** To see what is actually
being reported in a package:

```bash
pnpm --filter <pkg> exec eslint --max-warnings 0
```

Use that as a one-off diagnostic — don't bake `--max-warnings 0` into the `lint`
scripts without first clearing the existing warnings. As of this writing every
workspace reports 0 errors; the outstanding warnings are all
`turbo/no-undeclared-env-vars` for env vars not listed in `turbo.json`'s `env`
array (`SANITY_STUDIO_*`, `NEXT_PUBLIC_SANITY_*`, `SANITY_API_READ_TOKEN`,
`VERCEL_PROJECT_PRODUCTION_URL`). They are pre-existing and harmless at runtime —
each is read through a validated accessor or the Sanity CLI — but they are the
work to do first if lint is ever made blocking.

## Commands

```bash
pnpm lint                  # turbo lint — every workspace
pnpm --filter web lint     # one workspace
pnpm --filter <pkg> exec eslint --max-warnings 0   # reveal masked warnings
```
